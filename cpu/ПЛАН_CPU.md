Выводы:

- **генерация** упирается в пропускную способность памяти: скорость ≈ ГБ/с ÷ размер файла;
- **чтение запроса** упирается в вычисления, и здесь тернарная модель проигрывает обычной меньшей модели того же размера (4B-TQ2_0: 90 ток/с против 2B-Q6_K: 325). Это главная цель ускорения.

## Что делаем (по порядку)

1. **Замеры на Mac (ARM, NEON)** — сделано для Bonsai 2B (выше). Осталось: наши 0.8B/4B (нужен сервер, чтобы скопировать модели), `bench_mac.sh`.
2. **Профиль:** где тратится время при чтении запроса — ядро TQ2_0 × Q8_K, квантование активаций, FWHT, внимание, выходной слой на 248 тыс. слов.
3. **Ядро на таблицах подстановки (идея T-MAC / bitnet.cpp TL1/TL2)** для пакетного умножения TQ2_0 (чтение запроса): группы по 4 тернарных веса → индекс в таблицу из 81 заранее посчитанной суммы активаций; умножения не нужны, вместо них выборки (на NEON `vqtbl`, на AVX2 `vpshufb`). Ожидание по литературе: ×2–4 на чтении запроса. Сначала прототип вне ggml (замер на одной матрице), потом встраивание в ggml-cpu как отдельный путь для TQ2_0 при batch ≥ 8.
4. **Генерация:** проверить, достигает ли TQ2_0 пропускной способности памяти на Mac (M4 Pro ~273 ГБ/с); если нет — где теряем.
5. Если выйдет заметно — предложить изменения в основную ветку llama.cpp (лицензия MIT).

## Условия

- Mac: с 28.10.2026 пользователь разрешил замеры («пробуй»). Тяжёлое (обучение) по-прежнему только с защитой памяти, по одному процессу.
- Для x86 (офисные ПК) нужны отдельные замеры: AVX2 без AVX-512 — самый массовый случай.
